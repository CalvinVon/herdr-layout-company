让服务信息留在办公室墙上

本机项目办公室自动展示服务地址与原始二维码，保留服务停止状态；固定链接与原码可在重启后恢复。

阅读完整技术方案

预期数据流

下图表示拟实施的路径。观察进程的长期运行、原码提取和恢复边界仍需验证。

原码优先：终端二维码可能与旁边的 URL 不同。无法可靠恢复时显示提取失败并提供原终端入口，不能生成一个猜测的替源码。

交互与状态

  • 服务卡：服务输出更新时更新地址；有可信退出证据时标记停止，身份不确定或连接中断时标记未知。
  • 固定链接：可以手动添加、编辑、移除；本机重启后恢复，按已有项目房间隔离。
  • 墙面：紧凑展示数量和状态；打开原生详情后查看足够大的二维码、复制地址或定位终端。
  • 地址选择：Local 与 Network 分别显示；手机扫描不保证网络地址可达，localhost 指向扫码设备自身。

实施顺序

  1. U1 · 观察与身份：发现未标记的本机服务终端，读取历史并观察增量，处理退出、重连、切房间和未知状态。
  2. U2 · 二维码与界面：在墙面加入入口和原生详情，保真提取原码；展示、复制、打开与扫描。
  3. U3 · 固定与存储：按房间保存固定内容和手动链接，处理写入失败、冲突及重启恢复。

已经验证与仍需验证

规划期证据

  • 实际服务终端可读取到 Local 和 Network 地址；现有终端未带统一服务标签。
  • 受控探针的 URL 和文本二维码块字符可从历史读取；只读观察能接收后续输出。
  • 服务退出后 shell 可以继续存活，且前台程序变化时 PID 可能不变，因此不能只看终端状态或 PID。

实施验收

  • 在真实 Herdr 验证现有服务自动发现、房间隔离、停止与未知状态、热重载/断流恢复，以及观察者不输入、不调整尺寸。
  • 用真实 DRN 输出验证原码提取；用不同于相邻 URL 的载荷做对照，并通过手机扫描核对实际内容。
  • 验证窄窗口和多卡片布局、重启后本机存储恢复，以及损坏/冲突时的数据保护。
